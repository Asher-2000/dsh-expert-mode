# Expert Mode Pro 升级方案（优化版）

> 目标：Expert Mode 学习 dsh-agent-teams 的优点，又不失去自己的特点

---

## 🎯 设计目标

```
保留：11个专家人格 + 近距离引导 + 五锚约束
优化：锚定不降智 + 渐进披露 + 交叉评审 + 专家经验沉淀
原则：零破坏性变更，向后兼容，渐进式增强
```

---

## 🏗️ 现状分析

Expert Mode 当前是一个 **Agent Preset**（`.dsh/.agent-presets/expert-mode/`），核心结构：

```
expert-mode/
├── preset.yml              ← 元数据（名称+描述）
└── agent.cordis.yml        ← 核心配置
    ├── persona             ← 协调官身份 + 三锚约束
    ├── 11 个 expert_* 工具  ← 每个 = spawn子代理 + 独立persona
    └── 标准DSH工具          ← bash/fs/jobs/skills/goals 等
```

**关键限制**：
- 每次委派是**全新的 spawn 子代理**，用完即销毁
- 专家之间**零通信**，全部经过协调官中转
- **无状态持久化**，换会话全丢
- **无任务依赖管理**，协调官人工判断
- **11个专家persona全量注入**，初始token膨胀严重
- **无交叉评审机制**，高风险决策缺乏多角度验证

---

```
┌─────────────────────────────────────────────────────────────┐
│                     Expert Mode Pro（优化版）                 │
├─────────────────────────────────────────────────────────────┤

│  Layer 3: 协作引擎（任务DAG + 调度器 + mailbox）              │
├─────────────────────────────────────────────────────────────┤

├─────────────────────────────────────────────────────────────┤
│  Layer 1: 专家人格层（11个persona + 近距离引导 + 五锚）        │
├─────────────────────────────────────────────────────────────┤
│  Layer 0: 经验沉淀层（专家记忆 + 教训进化）                    │
└─────────────────────────────────────────────────────────────┘
```

## 📋 具体实施方案

### Phase 0：持久化专家会话（最大价值，最小改动）

**问题**：当前每个 `expert_*` 工具调用都是全新 spawn，用完即销毁。

**方案**：将专家子代理从 `一次性 spawn` 改为 `可续的 continuable 子代理`。

```yaml
# 现在（一次性）
- id: tool-subagent-expert-data-analyst
  name: '@deepseek-ai/dsh-tool-subagent'
  config:
    provider: spawn
    toolName: expert_data_analyst
    persona: "..."

# 升级后（可续）
- id: tool-subagent-expert-data-analyst
  name: '@deepseek-ai/dsh-tool-subagent'
  config:
    provider: spawn
    toolName: expert_data_analyst
    backgroundMode: continuable    # ← 关键：可唤醒续聊
    persona: "..."
```

**效果**：
- ✅ 专家完成任务后**不销毁**，保持在线
- ✅ 协调官可以**唤醒专家追加修改**，上下文完整
- ✅ 向后兼容，不影响现有委派逻辑
- ✅ 改动量极小，只加一行配置

### Phase 1：锚定智力不降智 + 渐进式披露

**来源**：dsh-anchored-flash 实验结论

**问题1**：系统 prompt 从 46 字突变到 6620 字，触发"轨迹翻转"，专家输出质量下降。

**问题2**：11个专家的persona全量加载，初始token膨胀严重。

**方案**：

```yaml
# 协调官persona优化：渐进式专家列表
# 现在：11个专家的完整persona一次性注入（~3000字）
# 优化：协调官只持有专家索引，委派时按需注入完整persona

专家索引（~300字）：
1. 数据分析师 - "先问业务→拆指标→找异常→给结论"
2. 文案撰写 - "先定画像→产多版本→差异化"
3. 合同/法务 - "先列要件→标风险→给修改建议"
4. 产品经理 - "需求澄清→用户故事→PRD→优先级"
5. 前端开发 - "技术选型→组件设计→性能优化"
6. UI/UX设计 - "用户流程→信息架构→视觉规范"
7. 架构师 - "需求→架构选型→模块拆分→决策"
8. 社交运营 - "平台组合→内容差异化→私域闭环"
9. 增长黑客 - "漏斗拆解→增长杠杆→实验验证"
10. 金融量化 - "数据→指标→模型→回测"
11. 财务 - "数据→报表拆解→预算归因→建议"
```

**子代理锚定**（参考 dsh-anchored-flash）：

```
专家子代理首轮只注入：
- persona摘要（~100字）
- 近距离引导模板（填入task/input/output）

完整方法论和铁律在专家开始工作后按需加载
→ 避免prompt突变导致推理风格翻转
```

### Phase 2：五锚约束升级

**现有三锚**：
```
【锚1·回顾】当前子任务是什么？上一步产出了什么？
【锚2·收敛】这一步的产出是否推进了总体目标？
【锚3·反跑题】连续2轮无实质进展 → 强制切换
```

**升级为五锚**：

```yaml
── 五锚约束（每轮强制自检，不可跳过） ──
【锚1·回顾】本轮开始前：当前子任务？上一步产出？
【锚2·收敛】本轮结束前：产出是否推进总体目标？
【锚3·反跑题】连续2轮无进展 → 强制切换策略
【锚4·协作检查】是否需要跨专家协作？路由是否正确？
【锚5·资源感知】上下文token占用是否健康？是否需要精简？
五锚不可省略，不可"心里想但不说"——必须显式输出锚点内容
```

---

### Phase 3：专家间通信协议

**问题**：专家之间完全隔离，所有信息必须经过协调官中转。

**方案**：在协调官 persona 中增加消息路由协议。

```yaml
── 专家间通信协议 ──
当任务需要跨专家协作时：
1. 让专家A完成后，通过 send_message 把结果发给专家B
2. 专家B收到后在自己的上下文中继续工作
3. 你负责路由决策：谁该把什么发给谁

通信格式：
[FROM:expert_data_analyst → TO:expert_frontend_dev]
任务：基于数据分析结论，设计前端数据展示组件
数据：{专家A的结论摘要}
```

---

### Phase 4：任务 DAG 状态层

**问题**：协调官人工判断任务依赖和执行顺序，容易遗漏。

**方案**：增加任务协调层，用 todo_write + 状态文件实现轻量 DAG。

**状态文件**（`.expert-mode/team-state.json`）：
```json
{
  "project": "项目名称",
  "created": "2026-08-18T15:00:00Z",
  "tasks": [
    {
      "id": "t1",
      "name": "产品需求定义",
      "assignee": "expert_product_manager",
      "status": "completed",
      "dependencies": [],
      "output_ref": "task-t1-result.md"
    },
    {
      "id": "t2",
      "name": "UI设计规范",
      "assignee": "expert_uiux_design",
      "status": "ready",
      "dependencies": ["t1"],
      "blocked_by": []
    }
  ]
}
```

```yaml
── 任务调度协议（复杂项目时启用） ──
当任务涉及 3+ 个专家且有依赖关系时：
1. 先拆解任务，写入 .expert-mode/team-state.json
2. 标注依赖关系（谁必须先完成）
3. 无依赖的任务并行委派
4. 有依赖的任务等前置完成后再唤醒对应专家
5. 每轮检查状态文件，推进下一步
```

### Phase 5：Token 预算意识

**来源**：dsh-headroom / billion-context-dsh 实践

```yaml
── Token 预算意识 ──
- 每个专家委派时，输出上限建议：2000字
- 汇总时只保留结论和关键数据，不搬运过程
- 超过3个专家并行时，先合并前两个结果再继续
- 定期检查上下文占用，超过70%时主动精简
- 专家经验沉淀只保留结论，不保留完整对话
```

---

### Phase 6：交叉评审机制

**来源**：dsh-ai-solution-council / ai-jury / agent-review-panel

**触发条件**（满足任一）：
- 用户明确要求"多角度验证"
- 高风险任务（架构选型、合同审查、金融分析）
- 专家输出置信度低（如"假设...""可能..."）

**执行流程**：
```
协调官识别需要交叉评审
  → 派给2-3个相关专家并行
  → 各自独立输出
  → 交叉评审：A审B的输出，B审A的输出
  → 协调官作为裁判汇总
  → 交付最终结论
```

**协调官persona追加**：
```yaml
── 交叉评审协议（高风险任务时启用） ──
当任务风险较高时：
1. 派给2-3个相关专家并行独立输出
2. 每个专家的输出作为其他专家的评审输入
3. 评审时标注"同意/部分同意/反对 + 理由"
4. 协调官作为裁判，综合评审意见给出最终结论
5. 评审记录保存到 .expert-mode/reviews/ 目录
```

---

### Phase 7：专家经验沉淀

**来源**：dsh-memory-evolve / dsh-mneme 实践

**方案**：每次任务完成后，专家自动提炼经验教训。

```
.expert-mode/
├── experts/
│   ├── data-analyst/
│   │   ├── persona.md          ← 核心人格（不变）
│   │   ├── methods.md          ← 方法论（可进化）
│   │   ├── iron-rules.md       ← 铁律（可追加）
│   │   ├── experience/         ← 历史任务经验
│   │   │   └── 2026-08-18-project-x.md
│   │   └── lessons.md          ← 踩坑教训（自动沉淀）
```

```yaml
── 经验沉淀协议 ──
每次专家完成任务后：
1. 提炼"这次学到了什么"（不超过3条）
2. 写入 .expert-mode/experts/{name}/lessons.md
3. 下次同类任务时，lessons.md作为额外上下文注入
4. 实现"越用越懂你"的进化效果
5. lessons.md超过20条时，自动归档最旧的到experience/
```

## 🆚 与 dsh-agent-teams 的定位差异

| | Expert Mode Pro | dsh-agent-teams |
|--|-----------------|-----------------|
| **核心哲学** | "每个人都要专业" | "团队要能协作" |
| **专家质量** | persona + 方法论 + 铁律 | 通用子 Agent |
| **委派精度** | 近距离引导模板 | 自然语言描述 |
| **协作能力** | 路由式（升级后） | 原生 mailbox |
| **智力稳定性** | 锚定不降智 | 无特殊机制 |
| **高风险决策** | 交叉评审 | 无特殊机制 |
| **经验积累** | 专家记忆进化 | 无特殊机制 |
| **适用场景** | 重专业输出质量 | 重多角色协作流程 |
